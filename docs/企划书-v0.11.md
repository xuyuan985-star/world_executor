## 三、Runtime Replay 提前至 M0（v0.10 最重要新增）

Replay 不是 GUI 功能，是**调试基础设施**。第一批就定义统一事件：

```
runtime/events/
  schema.py     # 事件类型 + 字段定义（冻结）
  bus.py        # 事件总线（线程安全，可订阅/持久化）
```

事件 schema（冻结）：

```json
{
  "id": "evt_001",
  "execution_id": "run001",
  "time": 12345,
  "type": "state_changed",
  "from": "NAVIGATING",
  "to": "RECOVERING",
  "context": {
    "room": "corridor_A",
    "portal": "door_B",
    "reason": "arrival_failed"
  }
}
```

事件类型（首批冻结）：

| type | 说明 |
|---|---|
| `run_started` / `run_finished` | 会话生命周期 |
| `state_changed` | 状态迁移（from/to/context） |
| `observation` | 观测记录（见 §四 Observation Contract） |
| `action_executed` | 步骤执行（move/click/portal/…） |
| `target_progress` | 目标队列进度（target_id/status） |
| `fail_recorded` / `repair_recorded` | fail_log / repair_log 镜像 |

- 事件总线落盘 → runtime.db（events 表），GUI 只是**播放器**。
- Replay 数据生成在 M0（dry_run + 真机共用同一总线），GUI-M0.1 只显示实时流，M0.3 做回放界面。

## 四、修正 1：Observation Contract（冻结格式）

所有视觉/观测结果**必须**进入统一格式，禁止各自打印/各自记录：

```json
{
  "observer": "template_match",
  "target": "door_A",
  "confidence": 0.91,
  "timestamp": 123456,
  "context": {
    "room": "corridor_A",
    "world_state": "quest_done"
  }
}
```

契约字段（冻结）：

- `observer`：template_match / ocr / ui_signal / inferred / manual
- `target`：观测对象（door_A / in_combat / menu_open / room_id …）
- `confidence`：0~1（inferred/manual 允许 null）
- `timestamp`：毫秒
- `context`：room / world_state / portal 等环境快照（可选）

runtime/db.py 的 `record_state_observation` 改为按此契约写入；所有模板/OCR 调用点统一走 `observer` 通道。

## 五、修正 2：Knowledge 目录规范（compiler 输出不可手改）

```
knowledge/
  raw/        # 上游素材：视频事件清单、VLM 输出（只读输入）
  source/     # 手写/人工确认的源知识（人可改）
  compiled/   # compiler 产物（禁止手改，validator 强制检查生成者标记）
  patches/    # 补丁层：运行时 repair 的落盘补丁（优先级最高）
```

- `compiled/` 内文件带生成者标记（`"generated_by": "compiler-v0.1", "generated_at": ...`），validator 检测到"compiled 文件被手改"→ error。
- 优先级：patches > compiled > source。
- 现状迁移：`knowledge/black_tower_test` 为**手写测试包**，归属 source/（Sprint 0 不动结构，M0 compiler 上线时迁移目录）。

## 附录 B：Execution Naturalness Policy（执行自然性约束）

> 定位：不是规避检测模块，也不是"模拟真人"，而是**执行质量约束**：避免固定 timing bug、降低机械误差、增强恢复能力。
> 原则：**降低机械化，不模拟外挂。** 本附录是执行器质量约束，不是能力模块。

### B.1 操作层随机化（Action Jitter）

禁止固定时间序列（`move 3000ms → sleep 500ms → click → sleep 1000ms`）；改为在合理区间内抖动：

```yaml
human_behavior:
  enabled: true
  delay:
    click:
      min_ms: 200
      max_ms: 800
    interaction:
      min_ms: 500
      max_ms: 1500
    transition_wait:
      jitter_ms: 1000
  movement:
    sprint_duration_variance: 0.15
    correction_interval_variance: 0.2
```

不追求随机，只消除完全固定的时间序列。

### B.2 移动行为约束（Movement Policy）

- 禁止：连续长距离完美直线 / 固定角速度旋转 / 每次停在完全相同位置。
- 允许：小幅方向修正 / 偶尔停顿 / 到目标附近提前减速。
- 实现：WASD 控制器前加 human movement filter（variance 见 B.1）。

### B.3 镜头行为限制（Camera Policy）

禁止 `yaw += 10°` 循环式机械扫描；保持 Heading Checkpoint（看到目标即停止旋转）。

```yaml
camera:
  max_continuous_rotate_s: 3
  search_pattern:
    - small_left
    - small_right
    - recenter
```

避免：无限扫描 / 高频左右抖动 / 完美角度锁定。

### B.4 行为节奏（Session Policy）

```yaml
session_policy:
  max_continuous_runtime_min: 60
  idle_break:
    enabled: true
    min_min: 3
    max_min: 10
```

用途：调试保护 / 防异常长时间运行 / 接近正常游戏节奏。

### B.5 错误处理策略（防无限重试）

```
fail → recover → 一次重新尝试 → 仍失败 → pause + human check
```

```yaml
recovery:
  max_retry:
    interaction: 2
    portal: 2
    movement: 3
  require_manual_after_limit: true
```

### B.6 日志增加 human_action 字段

```json
{
  "type": "action_executed",
  "action": "click",
  "target": "chest_01",
  "humanized": true,
  "delay_ms": 642
}
```

目的：分析失败 / 调整参数 / 对比自动化策略（不是隐藏行为）。

### B.7 L1/L2 安全等级调整

- **L1（默认）**：移动自动 / 镜头自动 / 交互确认 / 战斗人工 + `human_behavior=true`。
- **L2 = 高可信自动执行**（不叫"全自动"），要求：knowledge verified + confidence >0.8 + human_behavior enabled + 异常自动暂停。

### B.8 不做事项（防止跑偏）

❌ 随机鼠标轨迹生成器 / 模拟真人输入设备 / 反检测模块 / 行为对抗算法 / 绕过检测逻辑。
原因：会把项目从 World State Executor 变成自动化对抗系统，污染架构。

### B.9 落地时机

- M1 真机闭环前落地：Action Jitter + Movement/Camera Policy + Session Policy + 防无限重试（B.1~B.5）。
- B.6 随 runtime/events 已有 action_executed 扩展（加 humanized/delay_ms 字段，不新增事件类型）。

## 附录 C：真机执行边界条件（Operating Boundaries）

### C.1 宝箱状态识别（部分已开场景）

游戏机制事实：**崩铁普通/金色宝箱开启后从世界中永久消失，无刷新、无残留物**。

- 正确性**不依赖**已开状态记忆：每次进入房间实时检测现存宝箱（模板 + VLM 实体定位），已开过的不会出现 → 天然免疫"部分已开"，无假阳性。
- **禁止 `not found = opened` 的单一判定**（视觉会被遮挡/视角/加载/漏检污染）。判定走三级状态机：

```
not found
    ↓
secondary confirmation（换视角/走近/等待加载/二次 VLM 复检，≥2 个独立观测一致）
    ↓
opened / unknown（仍有疑义 → unknown，绝不写 opened）
```

- chest_state 三态：`present / opened / unknown`，只允许 opened 汇入 patches，unknown 不落盘不污染客观数据。
- verify 双通道（至少其一通过）：
  - **必做**：VLM 实体检测"宝箱实体不再出现在画面"（vlm locate → found=false 且未在别处）。
  - **辅助**：小地图宝箱图标存在性（若当前版本小地图显示图标；以实测为准）。
- 已开状态持久化（knowledge/patches）仅用于**效率**（跳过已清房间），不用于正确性。
- 执行记录每次开启写 `chest_opened` 事件（room/chest_id/时间）→ 汇入 patches 客观数据。

### C.2 登录归位与跨地图传送（Home Return Protocol）

风险：登录/启动后角色在**上次下线位置**，可能不在黑塔空间站（雅利洛VI/仙舟/匹诺康尼等）。

- Mission 开始前置流程（不可跳过）：
  1. UI 状态判定（游戏内/菜单/过场/战斗）——战斗不得开地图，先处理。
  2. 当前区域判定：大地图 OCR（左上角地图名）或 VLM room_detect 冲突时降级确认。
  3. 若不在黑塔空间站：M 打开地图 → OCR 左侧区域导航找「空间站『黑塔』」→ 展开舱段列表 → 点击「基座舱段」→ 点击目标锚点 → 等待加载 → 归位 Room Graph 入口（entry room）。
- March7th **无传送模块**，Home Return 为 WorldExecutor 自建（UI 状态机 + OCR + 锚点模板 + 加载等待），属于 M1 真机内容。
- 传送为锚点瞬移（免费无战斗），不触发战斗风险。
- 每次「无法判定当前区域」→ 默认走 Home Return 而非冒险执行。

### C.3 分辨率与坐标一致性

- 全链路坐标一律**相对坐标 (0-1 归一化)**：
  - March7th `find_image_element(relative=True)` 返回归一化坐标 → 由窗口矩形换算真实屏幕坐标（自动适配任意分辨率/窗口化/全屏，边框已由 `get_window_region` 校正）。
  - VLM 定位输出 0-1000 归一化 → /1000 后与模板通道同坐标系（已实现）。
- 模板匹配 scale_range 按分辨率适配：模板源 480p 视频，真机常见 1080p/1440p → scale_range 放宽 (0.9, 1.6) 起步，实测后按 `get_resolution()` 记录适配表。
- 截图缩放（screenshot_scale_factor）由 March7th 层处理，执行器不感知。

### C.4 窗口锁定与防误操作

- 锁定对象：窗口 title（cfg.game_title_name）唯一匹配；多开场景下校验 handle + title 双重匹配，不匹配立即 pause + human check。
- 每次操作序列前：`set_foreground_window_with_retry`（上游已有）激活窗口，防输入落空/落错窗口。
- 窗口矩形校验：每次操作前比对记录的窗口矩形，检测到用户拖动/缩放 → 重新激活 + 重新换算坐标 + 记录 window_moved 事件。
- 截图用 PrintWindow 后台捕获（上游已实现），遮挡/失焦不影响视觉通道；输入通道要求窗口激活（见上）。
- 用户手动介入（切窗口/操作游戏）不视为故障：检测到窗口失活 → 暂停等待 → 恢复前重新校验状态（房间/位置），不盲目继续。

## 附录 D：Architecture Boundary Rules（防腐层）

> 目的：冻结内容写的是"有什么"，本附录写"谁不能做什么"。任何 PR 违反以下规则即拒绝合并。

### D.1 Runtime 依赖方向

冻结依赖链：

```
knowledge → compiler → runtime → api/events → studio/gui
```

允许：
- GUI → runtime/api（唯一入口）
- runtime → knowledge reader（只读）
- compiler → schema validator

禁止（lint 检查 enforce）：
- GUI → step_executor / route_planner / observers 等内部模块（必须走 api）
- runtime → GUI（任何 import 即拒绝）
- step_executor → VLM 模型（observer 通道例外：executor 调用 observer 接口取观测，不得直接聊模型）
- movement_controller / planner → knowledge compiler
- observers → decision / executor

### D.2 模块职责边界

| 模块 | 可以做 | 禁止做 |
|---|---|---|
| Knowledge | 提供世界事实 | 决策执行 |
| Compiler | 生成执行图 | 控制游戏 |
| Planner | 选择路径 | 识别画面 |
| Executor | 执行动作 | 修改知识 |
| Observer | 提供观测 | 下执行命令 |
| Studio | 展示/调用 API | 直接操作游戏 |

**核心原则：Observer 可以告诉系统"看到了什么"，不能告诉系统"下一步怎么做"。**

### D.3 Observer → Decision 隔离

数据流必须经过决策层，禁止 observer 直接触发动作：

```
Observation {target, confidence} → Decision Layer {action, reason} → Executor
```

目录约束（lint enforce）：

```
runtime/
 ├── observers/   # 只能发布 observation 事件
 ├── decision/    # 消费 observation，产出 action 意图
 └── executor/    # 消费 action 意图，产出 action_executed
```

- Observer 永远不能 import executor/decision。
- Decision 永远不能 import executor 内部（只能发布 action 意图事件）。
- 现状（dry_run）decision 为确定性规则选择器（objective 顺序 + 状态机），M1 真机同样只走该层。

## 附录 E：里程碑拆分（M1-A / M1-B）

第一次真机失败时，必须能区分是哪个环节失败。因此 M1 拆为两段，**M1-A 完成前不开始 M1-B**：

### M1-A 纯执行闭环（验证执行器）

```
固定位置启动（人为放到基座舱段目标箱附近）
    ↓
识别箱（模板 + VLM 双通道）
    ↓
移动（visual guided move 短步）
    ↓
点击交互
    ↓
验证（secondary confirmation → opened）
    ↓
Replay
```

**不包含**：Home Return / Portal / World State / 跨房间。目的：只验证"识别→移动→交互→验证→Replay"执行器链。

### M1-B 真实任务（验证世界模型）

```
任意登录位置
    ↓
Home Return（附录 C.2）
    ↓
Portal（进入基座舱段）
    ↓
Room Graph 导航
    ↓
```
